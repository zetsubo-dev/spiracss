spiracss/class-structure

SpiraCSS の命名規則とセレクタ構造を検証します。

v0.5.0 から scope のコンポーネントルートに対応します。@scope (.test-card) を、直接宣言や子セレクタのルート Block として認識します。内側の :scope は必須ではありません。既存の所有関係・セレクタのネストの検査も維持します。生成設定と例は scope のルート書式 を参照してください。

目的

  • Block / Element の構造を機械的に判定できる状態に保つ
  • 親子構造の揺れを抑え、責務の分離を安定させる

検証内容

  • 命名（Block / Element / Modifier）
  • Block / Element の親子関係（Element > Block などを禁止）
  • Block 直下の > を強制（shared は緩和、interaction は構造検査の対象外）
  • Block の子セレクタは Block 内にネストして書く（トップレベルの .block > .child は不可）
  • shared / interaction セクションの配置位置
  • 1 ファイル 1 ルート Block（rootSingle）
  • ルート Block とファイル名の一致（rootFile）
  • selectorPolicy に応じた data/state の扱い

✅ 適切

❌ 不適切

理由

  • > を強制することで、親が子の並びを決める構造が明確になる
  • Element 連鎖は深さを制限し、責務の境界がブレにくくなる

例外 / 注意

  • shared セクションでは > の強制のみ緩和される
  • interaction セクションでは構造検証を行わない（命名検証は継続）
  • rootFile は *.module.scss を許可します（CSS Modules。.module は無視されます）
  • rootFile の検証で childDir 配下のファイル名は childFileCase を使います（設定オプション参照）

エラー一覧

rootScopeRequired（コンポーネントルートに scope が必要・v0.5.0+）

generator.scssRootStyle が scope / scope-explicit の場合、createRules() がこの検査を設定します。コンポーネントルートを .test-card { ... } と書くと、@container / @layer 内でもエラーです。ルート本体を @scope (.test-card) { :scope { ... } } で包みます。scope 直下形式も許可します。@use / @forward とページエントリのリンクコメントは scope の外に残し、meta.load-css() と Block セクションはルート本体の内側に置きます。子・孫 Block ファイルはクラス形式を維持し、子ファイル内のすべての @scope は別の lint エラーにします。診断には設定値・Block・修正例を含めます。以下のクラス形式の例は、子ファイルまたは class を選択したルートに適用します。

ルートの include 位置は維持してください。:scope の外に移すと子の詳細度が下がるため、修正として案内しません。子 scope の規約を参照してください。

childScopeNotAllowed（子ファイルはクラス形式・v0.5.0+）

設定された childDir 配下のすべての @scope をエラーにします。テーマの囲み・index・partial も対象です。子・孫のファイルに対して、ルート書式設定の値や直接ルールの設定有無、rootSingle / rootFile に関係なく適用します。判定範囲は配置規約であり、Sass の import グラフは解析しません。

設定したコンポーネント配置内では、子ディレクトリのサブツリー全体を認識します。その配置外では childDir 直下のファイルだけを子として認識します。深い配置には所有コンポーネントの配置設定が必要です。stdin で子コードを判定する場合もファイル名を渡してください。配置が未判定であることを、Sass 出力が安全である証拠にしないでください。

Sass は読み込み元の親セレクタを子 scope へ前置し、:scope を一致しない :scope :scope にすることがあります。子の scope を外し、クラス形式にしてください。

子ルートを参照する :scope は、子 Block のクラスか適切なネストの & に置き換えます。コンポーネントルートの scope と include 位置は維持してください。詳細度が変わる可能性があるため、自動修正は行いません。既存の子 scope は手動移行が必要ですが、ネイティブ CSS の入れ子自体を不正とする規約ではありません。

テーマの囲みは、その条件を維持して手動移行してください。単に囲みを削除すると、条件付きのスタイルが無条件に適用されます。上記のクラス形式の例を、テーマ scope の自動変換として使わないでください。

scopeOwnerAmbiguous（入れ子 scope の所有関係が不明・v0.5.0+）

Block 名を持つ scope が別の Block scope を囲む場合、所有関係の検査を暗黙に免除しません。コンポーネント名に一致するファイル名、または rootFile: false で一致するコンポーネントディレクトリ名を使ってください。どちらもない場合（stdin を含む）は、テーマの囲みを external.classes / external.prefixes で宣言します。テーマ名を勝手に推測したり、構造 lint を無効化したりしないでください。所有関係を識別できるコンポーネントルートのテーマ用囲みは許可します。
